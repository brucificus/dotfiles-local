Workflow for scraping a single LinkedIn `linkedin.com/jobs/view/<id>/` posting (read-only research, no apply). Companion to [[indeed-scrape-extraction]] — LinkedIn's markup is different enough to need its own recipe.

1. **Don't trust the `snapshot` YAML for the description body.** LinkedIn's job description text is wrapped in nested `text:`/`strong:` accessibility-tree nodes that render fine but are painful to reassemble from the YAML, and the file is often 1000+ lines (gets truncated by the Read tool at ~25k tokens, forcing pagination). Skip straight to `eval` with `--raw`.
2. **Full description via ID selector, with an expand click first:**
   - The description container's id is `JobDetails_AboutTheJob_<jobId>` (jobId = the numeric id from the URL).
   - There's a truncation/"…more" button with `data-testid="expandable-text-button"` inside that container — click it first: `eval "() => { const b = document.querySelector('[data-testid=\"expandable-text-button\"]'); if (b) b.click(); }" --raw`
   - Then pull clean verbatim text with real line breaks: `eval "() => document.querySelector('[id^=\"JobDetails_AboutTheJob_\"]').innerText" --raw`
   - Fallback if the id selector misses: find the `h2` containing "About the job" and read `.closest('section, div').innerText`.
3. **Open vs closed check:** `eval "() => document.body.innerText.includes('No longer accepting applications') || document.body.innerText.includes('no longer accepting') ? 'CLOSED' : 'open'" --raw`. Also cross-check that an "Apply"/"Save" button pair is present in `document.querySelector('main').innerText` — closed listings typically drop or grey out Apply.
4. **Header metadata (title, location, remote/on-site, employment type, salary if visible)** all come through cleanly in one shot via `eval "() => document.querySelector('main').innerText.slice(0,1500)"` — no need to click anything first; salary (when LinkedIn shows it) appears at the very end of the About-the-job text as a "Pay Range" line, so it's already captured by step 2's full-text pull too.
5. Open each listing in a **new tab** (`tab-new "<url>"`), not over the operator's existing tabs — same rule as Indeed scraping.
6. **Don't hunt for the expand button by text content ("Show more"/"…more") across the whole page.** LinkedIn job pages have several unrelated "Show more" links/spans (company insights, photos, etc.) — clicking a text-matched one can land on the wrong element, including an `<a>` that navigates the tab away to a Company/Life page. Always scope the query to the specific container first: `document.querySelector('[id^="JobDetails_AboutTheJob_"]').querySelector('[data-testid="expandable-text-button"]')`. Also note: on many postings the `innerText` of that container is already the full text with no truncation needed — check length/ending before assuming a click is required.
7. **If `[data-testid="expandable-text-button"]` isn't found** (seen 2026-07-22, layout variant), fall back to: take a `snapshot`, grep the saved YAML file for `more` (case-insensitive, content mode) to find the ref of the generic `… more` node (NOT the page-level "More"/"More options"/"Learn more" buttons — those are unrelated UI), then `click <ref>` directly. Confirm success by re-running `main.innerText` and checking the `… more` marker is gone — if the text before/after the click is otherwise identical, nothing was actually truncated and the click just removed the trailing marker.
8. **"No longer accepting applications" does NOT reliably predict whether the description body is present.** Seen 2026-08-04: two separately-closed listings rendered `document.body.innerText` at only ~1300 chars (just header + global nav/footer chrome, no "About the job" section at all — logged-out-looking minimal shell), while a third closed listing on the same session/tab set rendered the full ~9000-char page including complete "About the job" text. Don't assume a short `body.innerText` on a closed listing means you're logged out or blocked — it may just be how LinkedIn serves that particular expired posting. Always check `document.body.innerText.length`: if it's only ~1300-1400 chars (title/company/"No longer accepting applications"/footer only, no "About the job" heading), the description is genuinely unavailable server-side — report that plainly rather than retrying reload/re-attach.
8b. **`document.body.innerText` (not scoped to `main` or the AboutTheJob id) also works as a one-shot pull for open listings** — confirmed 2026-08-04 on an open Topstep Staff SWE posting: a single `eval "document.body.innerText" --raw` (piped to a file since it's long) captured the full "About the job" text already expanded (no click needed), applicant-click count, posted-age, and the "New Hire Base Salary Range" line, all in one call. Worth trying this simpler pull first before the scoped-selector dance in steps 2/6/7 when you just need everything and don't care about extra nav/footer noise.

10. **Generic button-text-match works fine as a first try, contradicting step 6's caution somewhat**: confirmed 2026-08-05 on an Intec Select posting — `[...document.querySelectorAll('button')].filter(b=>b.textContent.trim().includes('more'))` found exactly two "… more" buttons (About-the-job + About-the-company sections) and clicking both was safe (they're `<button>` elements, not `<a>` — the step-6 navigation-away risk was specifically about `<a>` "Show more" links elsewhere on the page). Still worth checking element tagName before a blind click-all if in doubt.

11. **8b's one-shot `document.body.innerText` pull also works on CLOSED listings, not just open ones**: confirmed 2026-08-04 on a VanderHouwen (via VanderHouwen recruiter) closed "Senior Software Engineer" posting — full "About the job" text, "No longer accepting applications" banner, applicant count (843), and pay range ($70-$80/hr) all came through in one `body.innerText` eval. When the `… more` truncation marker is still present, `snapshot` + grep for the `… more` generic ref (step 7's fallback) and click it, then re-pull `body.innerText` — worked cleanly even though this was a closed/expired listing (contradicts any assumption that closed listings only render the minimal 1300-char shell from step 8; that shell case seems to be the exception, not the rule).

13. **Gmail get_thread MCP tool (not just Brave-attach navigation) is a reliable way to find a specific job's tracked link inside a LinkedIn "jobs picked for you"/job-alert digest** when given only a Gmail permalink: `mcp__claude_ai_Gmail__get_thread` with the threadId from the URL fragment (`#all/<hex-id>`) worked directly on bruce.markham@gmail.com (u/1) without needing the illuminus86@gmail.com fallback this time. Output is often too large for the tool response and gets saved to a file — grep that file for the company name to find the surrounding `jobid_<N>` in the nearby `trk=` tracking params (multiple duplicate links per job — logo/title/body variants — all share the same jobid), then load `linkedin.com/jobs/view/<jobid>/` directly instead of clicking through the messy tracking-param URL.

12. **8b's one-shot pull confirmed again 2026-08-05 on Shamrock Foods Senior SWE (.NET) posting**: `document.body.innerText` (no scoping, no click) already contained the complete "About the job" text with no `… more` truncation inside it — the only `… more` buttons on the page belonged to unrelated sections (company focus-area insights, competitors blurb). Clicking all `… more` buttons blindly was harmless here (all were real `<button>`s) but added no new content to the job description itself. Lesson: always diff/read the description before-vs-after clicking anything — don't assume a click was necessary just because `… more` buttons exist elsewhere on the page.

9. **LinkedIn job-alert digest emails ("Your job alert for...") contain direct `linkedin.com/comm/jobs/view/<id>/...` links per posting**, even when the posting's employer name suggests a third-party board (e.g. "AgileGrid Solutions" turned out to be a LinkedIn-native listing whose body text says "About The Company: GrabJobs is..." — the recruiter/aggregator name appears *inside* the description, not as the link destination). Don't assume "posted via X aggregator" means you need to leave LinkedIn — check the email body for a `linkedin.com/comm/jobs/view/` link first; `/comm/jobs/view/<id>/` redirects fine to the normal `/jobs/view/<id>/` URL.
