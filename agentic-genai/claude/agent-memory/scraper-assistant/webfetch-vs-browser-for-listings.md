name: webfetch-vs-browser-for-listings
description: WebFetch alone is usually sufficient for both Indeed and LinkedIn job-status/stack checks without spinning up playwright-cli; fall back to browser only if a specific fetch comes back blocked/generic.
metadata:
  type: feedback
---

When re-checking an already-known job URL just to confirm open/closed status, stack, pay, or clearance language (not full first-pass scraping), try the plain **WebFetch** tool first before reaching for playwright-cli/browser automation — it's much cheaper per-listing when doing a large batch (e.g. routing 20+ kanban leads).

- **Indeed `viewjob?jk=...` pages**: WebFetch reliably renders the full JD text and clearly surfaces the "This job has expired on Indeed" banner when a listing is dead — no need to open a browser tab just to check liveness.
- **LinkedIn `jobs/view/<id>/` pages**: on a 2026-07-22 batch of ~30 listings, WebFetch succeeded cleanly on every single one — full JD text, applicant count, "no longer accepting applications" closure text when dead, pay/stack/degree/clearance all extracted in one call. Earlier notes here said LinkedIn was unreliable via WebFetch (sometimes returned a generic search-results page for an unrelated query on a stale job ID) — that failure mode still seems possible but is evidently not the common case. Try WebFetch first every time; only fall back to [[linkedin-jobview-extraction]] (playwright-cli against the operator's authenticated browser) if a specific fetch comes back as a generic/unrelated page.
- Ask the fetch prompt explicitly for open/closed status plus stack/pay/degree/clearance — a single well-targeted prompt covers all of it in one round trip.
- This complements [[indeed-scrape-extraction]] (which is for the heavier first-pass scrape-and-archive job) — use WebFetch for quick re-checks and even first-pass batch routing, playwright-cli only for full initial scraping or when WebFetch fails/is blocked on a specific listing.
- **2026-08-17 confirmation**: a `cts.indeed.com` tracked redirect link (and even the resolved `viewjob?jk=...` URL directly) hit Cloudflare's "Request Blocked" page in playwright-cli — both in a fresh unattached msedge session and via the redirect chain — no captcha to solve, just a hard block (Ray ID + IP shown). Operator's actual Edge instance couldn't be attached either (`attach --cdp=msedge` fails — remote debugging not enabled, see [[edge-attach-remote-debugging]]). WebFetch on the same `viewjob?jk=` URL worked cleanly on the first try: full verbatim JD text (asked explicitly for a verbatim code-block dump, not a summary), pay, remote/travel details, and apply-button/status banner all extracted correctly. **Takeaway: for cts.indeed.com links specifically, skip playwright-cli entirely and go straight to WebFetch** — don't burn a browser-open+navigate cycle first.
- Caveat unrelated to WebFetch reliability: when processing many company note files in one session, verify each file's actual listing URL with `grep -o 'linkedin.com/jobs/view/[0-9]*' file` right before fetching rather than trusting recollection — files can contain data-entry mismatches (a URL saved under the wrong company's card, confirmed by the JD text naming a different employer).
