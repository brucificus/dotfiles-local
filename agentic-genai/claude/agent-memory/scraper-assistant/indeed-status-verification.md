**Determining open/closed on an Indeed viewjob page**: visible page text is NOT reliable — a live listing can render with no visible "Posted X days ago" text and even no visible Apply button in the DOM (sidebar sometimes doesn't render depending on account/session state). Do NOT conclude "closed" just because Apply button/posted-date text is absent from `innerText` or the accessibility snapshot.

The reliable signal is in the page's embedded JSON-LD/state blob in `document.documentElement.outerHTML`: search for `"expired":true` or `"expired":false` (appears near `datePublished`, `normalizedTitle`, employer name). This is Indeed's own structured-data flag and is authoritative. Grep pattern: `/"expired"\s*:\s*(true|false)/i`. `datePublished` next to it is a JS epoch-ms timestamp — convert with `new Date(ms).toISOString()`.

Only trust visible "This job has expired on Indeed" text if it actually appears in `innerText` — the string also exists in Indeed's bundled i18n JSON as an unused template (e.g. `"This job has expired on Indeed":[null,""]`) even on live listings, so a raw HTML substring match on that phrase gives false positives. Match against `innerText`, not `outerHTML`, for the human-visible banner; use the `expired` JSON flag as the primary check regardless.

**cts.indeed.com tracked redirect links (from email digests) previously returned HTTP 403 from Cloudflare** when hit via WebFetch, curl, or an unattached/fresh Playwright browser — these methods lack cookies/fingerprint Cloudflare trusts. **UPDATE (2026-08-04): they resolve fine via `playwright-cli goto` inside a session attached to the operator's real, already-authenticated browser** (`attach --cdp=http://localhost:9222`, see [[edge-attach-remote-debugging]]) — confirmed twice in one batch, each `goto` on a cts.indeed.com URL cleanly redirected to the canonical `indeed.com/viewjob?jk=...` page with no 403. So: WebFetch/curl/unattached-browser on cts.indeed.com links = still expect 403; attached-to-real-browser `goto` = works. Try the attached-browser route before giving up and handing back to the user.

**Why**: burned time assuming absent apply-button/posted-date text meant "closed" when the authoritative `expired` JSON field said otherwise; separately wasted several attempts trying to auto-resolve cts.indeed.com links with tools that don't carry Cloudflare-trusted session/cookie state.

**UPDATE (2026-08-30b): `expiredJobMetadataModel:null` is NOT a reliable "live" signal — it can be `null` on a confirmed-expired job.** On jk=c42553ce4a586efc (Komatsu America "Engineer III, Embedded Software Developer") the page had `"isJobExpired":true` in `outerHTML` AND rendered the visible "This job has expired on Indeed" banner at the top of `#main` content, yet `jobInfoWrapperModel...expiredJobMetadataModel` was still `null`. Precedence for a verdict: (1) visible "This job has expired on Indeed" text in `body.innerText` and (2) `"isJobExpired":true` are each authoritative for EXPIRED — either one alone = EXPIRED. `expiredJobMetadataModel` populated also = EXPIRED, but `expiredJobMetadataModel:null` proves nothing on its own. Note also: on an expired job the full JD body still renders (Komatsu one had a complete multi-section description, ~6300-char body) and there is NO apply button/`applystart` link at all — so "description renders" is not a live signal either.

**How to apply**: for any Indeed status-check task, go straight to the `"expired":`/`"isJobExpired":` flag via `eval` on `document.documentElement.outerHTML` (works from a `#jobDescriptionText` or general script-tag grep too — `[...document.querySelectorAll('script')].find(s=>s.textContent.includes('"expired"'))`). For cts.indeed.com links from email digests, attach to the operator's live browser first and `goto` the link directly — don't preemptively hand back to the user.

**UPDATE (2026-08-05)**: confirmed again that an unattached fresh Playwright browser gets a hard Cloudflare "Request Blocked" page (not even a 403 body, just the block page) on both the raw `cts.indeed.com/...` link and the resolved `indeed.com/rc/clk?jk=...` / `indeed.com/viewjob?jk=...` URLs. Tried falling back to `attach --cdp=msedge` per [[edge-attach-remote-debugging]] and it failed — that operator Edge instance didn't have remote debugging enabled this session, so the attach route isn't a guaranteed fallback; confirm remote debugging is actually on before counting on it.

**WebFetch DOES get past the Cloudflare block** (unlike the unattached browser) and reliably returns the `expired` status, title, company, location, and salary as plain facts. Earlier testing suggested WebFetch enforces a hard ~125-character cap per verbatim quote and refuses/paraphrases full job descriptions — **that no longer held up (2026-08-17)**: a prompt explicitly asking to "reproduce the exact raw text ... character-for-character, with no summarization, paraphrasing, or omission ... wrap in a code block" returned the complete multi-paragraph JD (PerfectServe Sr. SWE .NET listing, jk=da09fde12c4a09ec) with formatting (bold headers, bullet nesting) intact and even preserved an odd leftover editing artifact (`[MA1.1]`) that a paraphrase would never invent — strong evidence it was genuine raw extraction, not summarization. So: when full verbatim body text is needed and the browser route is Cloudflare-blocked with no CDP attach available, try WebFetch with an explicit "verbatim/character-for-character/code block" instruction before concluding the text is unobtainable — it may now succeed where a generic "get the job description" prompt would paraphrase or truncate.

**Also confirmed (2026-08-17)**: the Cloudflare block on a fresh unattached Playwright msedge session can hit even the bare `indeed.com` homepage (not just deep viewjob/tracked links) — i.e. the whole domain gets blocked for that browser fingerprint/IP, not just specific URL patterns.

**UPDATE (2026-08-30): newer Indeed viewjob page state blob may have NO `"expired":`/`isJobExpired` key at all.** On jk=4255a5a72a835662 (GigXR Unity Engineer) attached to operator's real browser, `outerHTML` contained no `isJobExpired` or `"expired":` flag; the only `xpired` hits were unrelated A/B allocation names (`g4j_expired_vj_recommended_jobs_tst`, `isExpiredVjRecommendedJobsActive`). The authoritative liveness signal in this layout: `jobInfoWrapperModel.jobInfoModel.expiredJobMetadataModel` — `null` = LIVE, populated = expired. Sibling `appliedStateBannerModel` is also `null` on a clean live job. Grep `expiredJobMetadataModel` and read the value. Corroborate with: full JD renders under "Full job description" (note: `#jobDescriptionText` selector no longer present — text is in a different container), a real `<a>` to `indeed.com/applystart?jk=...` exists, and no "expired/no longer available" phrase in `innerText`.
