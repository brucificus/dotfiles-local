The vault's active job hunt is tracked at `Projects/Y2026Q3 Job Hunt/Y2026Q3 Job Hunt.md`, an obsidian-kanban board (`kanban-plugin: board`). Per-company lead "cards" live in `Resources/Kanban Tasks/` (a few legacy ones live under `Areas/Employment Continuity/Y2023 Q1 Job Hunt/` and are still linked from the current board).

Card note convention (observed across ~20 existing cards):
```
---
created: YYYY-MM-DD
modified: YYYY-MM-DD
kind: kanban/jobhunt
tags:
  - opportunities/employment
---

### Log

#### Y2026 W{isoWeek} {MM}-{DD} {Weekday} (D{dayOfYear})

<freeform content — usually just a LinkedIn job URL, sometimes job description blockquotes or notes>
```
Log entries are ascending chronological — oldest at the TOP, most recent appended at the BOTTOM of the `### Log` section — each under its own `####` dated heading. Corrected 2026-06-30 per direct operator feedback (a prior version of this memory incorrectly said newest-first/reverse-chronological; that was wrong — see [[feedback-job-hunt-handoff-conflicts]]). When adding a new entry: if today's date heading already exists, append the new role block(s) at the bottom of that heading's content (after any earlier-logged entries for the same day), not above them. If it's a new day, add a new `####` heading after all existing ones, at the end of the file. Date-heading format uses true ISO week number (Monday=week start) and day-of-year zero-padded to 3 digits, e.g. 2026-06-30 (Tuesday) = `Y2026 W27 06-30 Tuesday (D181)`.

The board's "Ideas" column is the intake/triage list (least-evaluated leads). Disqualification columns: "❌ Disqualied, Courting Recency" (recently/unfavorably applied — doubles as proscription list), "❌ Disqualified, Culture", "❌ Disqualified, Location". Pipeline columns after Ideas: Courting Awaiting Them/Me, Courting/Screening Call Scheduled, Screening Awaiting Them/Me, Closed.

Master scraper guidance + proscription list lives at `Projects/Y2026Q3 Job Hunt/202606301256 Job Hunt Guidance for Scraper Assistant.md` — companies in the board's "Disqualified, Courting Recency" column are mirrored there as "Recent Applications" (proscribed). Always cross-check new leads against both before adding.

Board-column insertion/ordering rules are per-task, not fixed — confirm with the operator each time rather than assuming. Observed so far: (1) merging new leads into an existing column without disturbing current order; (2) inserting a new block at the top of "Ideas" sorted by fit descending; (3) re-sorting the ENTIRE "Ideas" column by fit descending with no-fit entries settled to the bottom (done 2026-06-30, ~97 entries). For (3) and any other fit-based sort: when a card has multiple logged postings (multiple `Fit X.X/5.0` values from the one-card-per-company rule), use the card's MAXIMUM logged fit value as its representative fit. Cards with zero logged fit values (legacy bare-URL cards predating the fit-scoring format, plus very old `Areas/Employment Continuity/Y2023 Q1 Job Hunt/` cards) count as "no fit estimation" and sort after all fit-bearing cards; ties (including the no-fit group) are broken by preserving the cards' prior relative order in the column rather than inventing a secondary sort key.

(4) Once the board has been explicitly sorted (per (3)), treat that sort as the new baseline: subsequent handoffs (even without a fresh sort instruction) get inserted at their correct descending-fit position within the existing order, not appended/prepended in a block — this preserves the operator's just-established sort rather than silently re-breaking it. This includes re-positioning an EXISTING card whose representative (max) fit changes because a new posting was logged on it (e.g. R Systems jumped from the 1.6 tier to the 2.0 tier on 2026-06-30 after a new Indeed posting raised its max fit) — move its single board-row reference, do not duplicate it.

Lead sources seen so far: LinkedIn (scraper-assistant agent, `/handoff` of job search result pages) and Indeed (same mechanism, different site) — both funnel into the same per-company card format and the same board. Indeed handoffs observed so far omit a posting URL and "posted X ago" field (LinkedIn handoffs include both); when URL is absent, just omit that bullet rather than inventing one.

(5) When a handoff entry's company matches an existing card already in the "❌ Disqualied, Courting Recency" column (= the guidance file's "Recent Applications" proscription list), skip it entirely — do not create a card, do not add a board row, do not log it on the existing disqualified card. Confirm the match by reading the existing card's content (not just company-name string match) since names can differ slightly (e.g. board/proscription list says "🏢 Spire", an Indeed handoff said "Spire Global" — same company, confirmed via the card's job-description text). Always still report the skip to the operator in the summary rather than silently dropping it from the conversation.

(6) When a new handoff posting on an EXISTING card has the same title + location/work-model as a posting already logged on that card but can't be confirmed as the literal same listing (e.g. no URL on one side to compare), log it as a separate dated sub-entry anyway (don't silently dedupe/discard) and add a `> [!conflict]` callout immediately above the new entry explaining the suspected overlap, for the operator to resolve. This mirrors the existing pattern already used on `Sierra Space.md` for a likely re-posted/refreshed requisition.

(7) Indeed handoffs starting 2026-06-30 (page 3 onward) began including a `jk=` posting URL per row. When a new handoff row's title/pay/location exactly match an already-logged entry on an existing card, treat it as a CONFIRMED duplicate (not merely suspected) and add the URL to the existing entry as a new `- URL: https://www.indeed.com/viewjob?jk=...` bullet — do not create a new sub-entry or `[!conflict]` callout for these, since the URL removes the ambiguity that motivated rule (6). Reserve `[!conflict]` for cases where the SAME posting (same title/pay/location/URL) was scored with a DIFFERENT fit value across two separate scrapes — that's a fit-scoring inconsistency to flag for the operator, not a new posting (precedent: Auria's "DevSecOps Engineer" scored 1.8 on page 1 and 1.4 on the page-3 re-scrape of the identical `jk=` listing, 2026-06-30). Genuinely different postings on an already-tracked company (different title, e.g. a different product team or role) still get logged as new sub-entries as normal, and if the new posting raises the card's max fit, reposition its board row per rule (4) (precedent: Homebase 2.3→2.9 tier, 2026-06-30, after a new "Senior Software Engineer II" posting).

(8) Legally-distinct-but-related subsidiary entities get SEPARATE cards (not merged into the parent's card), cross-linked with a `> [!note]` callout pointing to the other card. Precedents: Sierra Nevada Corporation ↔ Sierra Space; Rocket Lab ↔ PSC by Rocket Lab (pre-existing on the board before this project); Amazon ↔ Amazon Web Services, Inc. (2026-06-30, since the two brands' postings are genuinely different roles/teams).

(9) A legacy no-fit card (see (3)) that gains its first-ever `Fit X.X/5.0` value from a new handoff posting must be repositioned out of the no-fit tail group into its correct descending-fit tier, same as rule (4)'s reposition case — it's just the boundary case where "prior fit" is "none" rather than "lower." Precedent: `Speechify.md` (two legacy bare LinkedIn URLs, no fit) gained a Fit 3.4 Indeed posting on 2026-06-30 and moved from the no-fit tail up to the 3.4 tier, between Ledgent Technology (3.5) and Centraprise (3.0).

(10) Board fit-sort is not perfectly reliable at every position — spot-checking during Task 8 (2026-06-30) found `Cymertek Corporation.md`'s actual card fit is 2.0, but its board row sits between the 2.8 tier (Allegion) and the 2.6 tier (Peaksware/Mostest), i.e. it's misplaced roughly 0.6-0.8 too high. Left uncorrected/unrepositioned (flagged to operator instead) since fixing it wasn't in scope and no fresh full-column re-sort was requested — but if the operator ever asks for another full re-sort pass (per (3)), don't trust board position alone as a proxy for a card's fit; re-read the actual card content to get the true MAX-fit value, the way rule (3)/(9) already require for newly-inserted rows.

(11) Recruiting/staffing-agency postings sometimes list the AGENCY as the "Company" (not the real hiring employer), and separately some postings carry absurdly-low pay for the stated title (e.g. a "Lead" role at $12k-15k/yr — nonviable as a real US salaried role). Neither triggers a guidance-file blanket disqualifier (those are about clearance/degree/language/executive-level only), so these still get a card + board row, but flag with `> [!caution]` rather than silently including or unilaterally excluding. Precedents (Task 9, 2026-06-30): `TechBiz Global GmbH.md` (agency name as employer, no pay listed) and `Two95 International Inc..md` (Fit 0.3 — lowest ever logged on this board — for a $12k-15k/yr "Lead" title). `[!caution]` is also the right callout (not a hard exclusion) for softer GovCon/defense-adjacent "smell" that doesn't explicitly state a clearance requirement — precedent extended this task to `Steampunk.md` (McLean, VA) and `PEOPLE TECHNOLOGY AND PROCESSES LLC.md` (Alexandria, VA + M365 security/QA scope).

(12) When a handoff's fit values need placement among MANY intermediate board cards whose exact fits aren't already known from prior tasks' anchors (i.e. more than 2-3 unknown gaps to bridge), don't guess from nearest known anchors — instead run one bulk `Grep` across the whole `Resources/Kanban Tasks` folder for pattern `— Fit \d\.\d/5\.0` with `output_mode: content`, `-o: true`, `head_limit: 0` to extract every existing card's exact fit value(s) (with filenames) in a single call, then build the full insertion plan from that ground truth. Precedent: Task 10 (2026-06-30, 15 new companies spanning fits 2.4→0.8) — this was materially more accurate than the "nearest known anchor" heuristic used in Tasks 8-9 and resolved all ambiguity in one pass.

(13) Edit calls against `Y2026Q3 Job Hunt.md` have repeatedly (Tasks 9 and 10, 2026-06-30) failed on the first attempt with `"File has not been read yet. Read it first before writing to it."` even when the file had already been read earlier in the same turn/conversation. This is systematic, not a one-off — always issue a fresh `Read` of this specific file immediately before every batch of `Edit` calls against it, no exceptions, even if it was read minutes earlier in the same session. Task 11 (2026-06-30) showed this same stale-read-state error can hit ANY file (it hit this very memory file mid-edit), not just the board — treat "Edit fails with this exact message" as always fixable by a fresh Read immediately before retrying, regardless of which file.

(14) `[!caution]` also applies to non-US remote-labeled roles (e.g. a posting explicitly tagged "(Argentina)" for a "Remote" role — precedent: `Arize AI.md`, Fit 1.0, 2026-06-30) since the guidance floor ($120k/yr+ US salaried) implicitly assumes a US-based role even when location isn't a guidance-file blanket disqualifier. Also reinforced this task: `Arcfield.md` (ex-Leidos IS&GS defense/intel lineage) and `Slingshot Aerospace.md` (space-domain-awareness = defense/intel customer base) both got the GovCon-smell `[!caution]` treatment per rule (11), and `UST.md` got the staffing-shop + pay-under-floor `[!caution]` combo.

(15) Direct human-outreach leads (recruiter InMail/email awaiting Bruce's reply, not yet a scheduled call) belong in the "Courting, Awaiting Me" column, not "Ideas" — precedent: Framatome (Protingent recruiter) and Maania (staffing-agency recruiter for an undisclosed federal-contract employer), both 2026-07-02, filed there since Bruce owed a reply (call-scheduling / resume+salary ask) rather than being unvetted candidates. When the handoff item is an email/inbox summary rather than a scraped listing (no fit-scoring methodology applied), don't fabricate a `Fit X.X/5.0` value — write "Fit not scored (recruiter inbound/email digest, no listing scraped)" instead, and add a normal `> [!caution]` if guidance-file criteria (clearance requirement, sub-market salary for the stated level, agency-not-real-employer per rule (11)) apply. Precedent: Maania's federal role requires a security clearance, which trips the guidance file's "Blanket Disqualifiers" clearance clause (only exempted "when already employed" — Bruce is currently unemployed) — flagged with `[!caution]` rather than silently skipped, since it's a live human conversation the operator still needs to see and decide on himself, unlike the entity-level Proscriptions list in rule (5)/(from feedback memory) which does warrant a silent skip.

(16) When a Tier-3-style handoff bundles ~20 recurring automated LinkedIn job-alert postings (low-signal, not personal outreach), the judgment call that held up: only touch companies that ALREADY have a card on the board — append a dated log entry (or a same-day `[!conflict]`/note if it looks like the same requisition resurfacing without a URL to confirm). Do NOT create brand-new cards for alert-only companies with no existing card — treat those as pure noise per the handoff's own framing and just report them as skipped. Precedent: 2026-07-02 handoff — appended to BridgeView/Compa/Optum/Homebase/MiTek/DAT (all already tracked), skipped ~10 never-before-seen alert companies (Northreach, One Call, OPENLANE, GoodRx, Rubrik/Mastercard, Elios, Northwest Partners, RBA Inc., UVA Health, Boost Mobile) entirely with no card/board row.

(17) If a Tier-3 item's exact company+title+date combo is ALREADY present verbatim in an existing card's log (e.g. an inbox-scan bullet list already recorded that same LinkedIn alert on a prior task), don't touch the card again — just note the redundancy in the final report. Precedent: Bayview Asset Management, LLC's "Software Engineer (Full Stack)" alert dated 2026-06-26 was already logged verbatim in the card from a prior task's inbox-scan bullet list.
