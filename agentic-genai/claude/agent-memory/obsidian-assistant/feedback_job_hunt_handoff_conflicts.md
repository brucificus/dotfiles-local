When importing a scraper-assistant job-lead handoff into [[project-job-hunt-kanban]], never silently merge a new lead into an existing company card without flagging it. If a company already has a card anywhere on the board (Ideas or a disqualified column), do not add a second board entry for it — instead append a new dated `#### ` log entry to the EXISTING card containing the new posting's full details, and prepend it with a `> [!conflict] ...` callout explaining exactly what's ambiguous (e.g. "same title, different URL — unclear if re-surfaced posting or new req" or "operator already dismissed this employer's postings, re-flagging rather than re-adding").

Why: operator explicitly wants manual resolution of ambiguity (e.g. is this literally the same job re-scraped, or a new opening) rather than an agent guessing. Confirmed via direct task instruction 2026-06-30.

How to apply: Before creating any new card, search the whole vault (not just the board) for the company name — cards can also live in `Areas/Employment Continuity/...` from older job hunts. Also diff the new posting's job title/URL against the existing card's most recent entries to judge whether it's plausibly the same requisition resurfacing (LinkedIn often re-shows the same opening under a fresh listing ID) vs. genuinely new.

When a handoff contains duplicate postings for the literal same role (e.g. same title/company at two LinkedIn URLs, different cities for the same listing), collapse to ONE card and flag the duplication in a `> [!conflict]` callout inside that card rather than creating two cards or silently picking one.

**Standing rule: exactly one card per company, full stop — regardless of how many listings/postings that company has out at once.** Operator confirmed 2026-06-30: "HR departments for software dev are always a singular funnel that doesn't tolerate concurrent applications." This applies even beyond the literal-duplicate case above — e.g. two genuinely DIFFERENT open roles at the same company (different titles, different teams) still collapse into one card, with each posting logged as its own dated entry on that single card. Never create a second card for a company that already has one anywhere in the vault, even if the new listing is for a distinct role.

**Correction, 2026-06-30:** Log sections are ascending-chronological — oldest entry at top, most recent appended at the bottom — NOT reverse-chronological as an earlier version of this memory said. Operator corrected directly: "Log sections in my notes are always meant to be in ascending order of date, most recent entry at end." Applies to both the ordering of `#### ` dated headings within a card (oldest heading first, newest heading last/appended at file end) and the ordering of entries within a single same-day heading (earliest-logged-today first, most-recently-logged-today last). When a card already has a `#### ` heading for today's date (e.g. from an earlier handoff batch processed the same day), don't create a second same-day heading — append the new role block(s) under the EXISTING today-heading, BELOW the earlier same-day content, each as its own `**Title** — Fit X/5.0` sub-block with its own Source line. See [[project-job-hunt-kanban]] for the corrected card-format reference.

If a card's company also appears in the guidance file's "Infamously Bad Fit" or other proscription-adjacent list (e.g. KPMG US) but is still sitting in the board's active "Ideas" column rather than a disqualified column, that's a mismatch worth a `> [!caution]` callout on the card — don't silently resolve it (board/guidance reconciliation is the operator's call) and don't move the card between columns yourself.

A literal duplicate URL re-scraped in a later page/batch needs no new dated Log entry — just a short `> [!note] Re-surfaced in page N scrape` line appended after the existing entry's Source line, noting the date and URL match.

When the same exact posting (same URL) appears twice within a single handoff table under two slightly different spellings of the company name (e.g. "Yorkshire Global" vs. "Yorkshire Global Solutions Inc."), collapse to one card under the fuller/more formal name and note the spelling variant in a `> [!conflict]` callout — don't create two cards or silently pick a name without explanation.

Don't re-note cards that were created or updated only minutes earlier in the SAME session, even if their URL reappears in a later, broader handoff batch that overlaps page ranges with the earlier one (e.g. "page 2" then "pages 2-4 combined" requested back-to-back). Treat these as the same operator session's natural overlap rather than a new re-surfacing worth flagging — just mention the dedup count in the final summary report instead of touching the card again.

**Guidance-file proscriptions take precedence over a scraper handoff's own framing, even when the handoff explicitly says a company is "not proscribed, your call."** Confirmed 2026-06-30: a pages-2-4 handoff described Lockheed Martin and CACI International as "clearance-risk, flagged near floor, not proscribed" — but both were already listed under the guidance file's "Infamously Bad Fit" section, which falls under "Proscriptions" (skip entirely). Resolution: skip them outright (no card, no board row), and call this out explicitly in the final report so the operator knows the scraper's framing was overridden. Only treat genuinely unlisted clearance-adjacent companies (e.g. Sierra Space, York Space Systems, Social Security Administration, Boom Supersonic) as normal leads with a `> [!caution]` callout — don't formalize them as proscribed on your own initiative, but don't ignore an existing proscription just because a handoff says it's discretionary either.

When a card's Log entries accumulate enough new postings that its true best-fit value rises well above its current board position (e.g. a card sitting low in Ideas suddenly gets a much-higher-fit posting added), do NOT move the row — note the mismatch in a `> [!note]` callout on the card instead and let the operator decide whether to manually reposition it. Existing board row order is never disturbed by an update to an existing card, only by inserting brand-new rows.

**Board insertion point is per-task, not a fixed convention — check the literal instruction each time.** Tasks 1 & 2 (2026-06-30) used a "merge into existing order by fit, don't disturb pre-existing rows" approach because that's what was asked. Task 3 (same day) explicitly said "New entries go at the top of 'Ideas' section, sorted descending by fit rating" — a different placement rule — so all brand-new company rows were inserted as one contiguous block at the very top of Ideas, sorted descending by fit among themselves, ahead of all pre-existing rows (which were left untouched/unmoved). Don't assume one placement convention carries over; read each handoff's explicit instruction for where new rows go.
