name: indeed-cts-link-stale-redirect
description: cts.indeed.com tracked link in an old Indeed match email can reproducibly redirect to a totally unrelated job posting, not 403 or expire
metadata:
  type: project
---

A `cts.indeed.com` tracked "View job"/title/"Learn more" link from an Indeed personalized-match email (all three elements share the identical href) can, on repeat visits weeks later, consistently redirect to a **different, unrelated job posting** rather than 403ing or showing an expired-job page. Reproduced twice in a row (same wrong destination both times) navigating the exact same href extracted via `outerHTML`/eval — ruled out extraction bugs. This extends [[indeed-status-verification]] (which covered the 403 case) with a second stale-link failure mode: silent wrong-destination redirect, likely because cts.indeed.com serves a "next recommended job" once the original posting is delisted rather than erroring.

**Why:** Task required following the tracked link through to the specific posting; got routed to a completely different job (different company, different jk) both times, which would have produced a wrong report if not caught by verifying company/title match on the landing page.

**How to apply:** After following any cts.indeed.com tracked link, verify the landing page's job title/company text actually matches the source email before trusting jk/description/status — do not assume redirect target is correct just because navigation succeeded (200, not an error page). If landing page doesn't match, fall back to `indeed.com/jobs?q=<title>&l=<location>` and `q=<company> <keyword>` searches. If the company+keyword search also returns zero/unrelated results and the company's own active listings (searched by company name alone) don't include the role either, treat the posting as very likely expired/delisted and report that plainly rather than guessing — Indeed's search index appears to drop expired listings entirely (no expired-job page reachable without the jk).

**UPDATE (2026-08-17) — third failure mode, `net::ERR_HTTP_RESPONSE_CODE_FAILURE`:** In an attached, authenticated-browser session (`goto` via `attach --cdp=http://localhost:9222`, cookies present, other cts.indeed.com links on the same page resolved fine), one specific cts.indeed.com tracked link failed hard navigation with `net::ERR_HTTP_RESPONSE_CODE_FAILURE` — not a 403, not a redirect, not a page render — reproduced on retry. This is a third distinct cts.indeed.com breakage mode beyond the 403 ([[indeed-status-verification]]) and wrong-destination redirect (above) cases. **Recovery that worked:** the company's own Indeed `cmp/<Company>/jobs` page listed a job card with the exact title from the source email; scraping `data-jk`/`a.jcs-JobTitle` attributes off that page found the matching jk, and `goto https://www.indeed.com/viewjob?jk=<jk>` loaded the listing cleanly (verbatim `#jobDescriptionText` + `"expired":false` both worked normally once on a direct jk URL). So: when a cts.indeed.com link throws a hard navigation error (not a 403 body), don't retry it — go straight to the employer's `cmp/<Company>/jobs` page, match by exact title text, extract `data-jk`, and hit `viewjob?jk=` directly.
